# Специфікація нового онбординг-опитувальника NutriDay

Статус: узгоджено, готово до реалізації.
Передумови й розбір референсу — [BETTERME_QUIZ_TEARDOWN.md](BETTERME_QUIZ_TEARDOWN.md).

## Цілі

1. Одне питання на екран, лічильник кроків, кнопка «Назад» — за макетом бренд-буку (слайд 8).
2. Пояснення «навіщо це питання» і «що ти отримаєш» — підписи під питаннями + інфо-екрани.
3. Підвищення довіри — соц-доказ, прозорість розрахунку, експерт, дисклеймер, точкові згоди.
4. Стилі за бренд-буком Nutriday.
5. Флоу описаний **даними**, а не 18 сторінками зі `switch`-навігацією.

## Прийняті рішення

| Питання                                    | Рішення                                                                    |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| Довжина квізу                              | Довільна — макет у бренд-буку («ПИТАННЯ 2 З 4») це приклад, не обмеження   |
| Алергії / нелюбимі / улюблені продукти     | **Не питаємо.** Вносяться в профілі після оплати                           |
| `nutritionKnowledge`                       | **Залишаємо** — керує багатослівністю пояснень                             |
| Решта 7 мертвих полів                      | Видалити                                                                   |
| Вік діапазоном на початку                  | **Прибрати** — тільки точний вік у групі «Тіло»                            |
| Крок 41 BetterMe (інтервальне голодування) | Залишаємо, переписаний без згадки голодування                              |
| Крок 42 BetterMe (перерва від голодування) | Замінено на «Чи любиш готувати одразу на кілька днів?»                     |
| Дані, які генератор ще не вміє читати      | Збираємо зараз, використовуємо потім — пуші, нагадування, мотивація        |
| Інфо-екрани B5, B9                         | Скріни з застосунку, не мальовані макети                                   |
| Відгуки в лоадері                          | Не показуємо — немає справжніх                                             |
| Email                                      | Переїжджає зі сторінки оплати в онбординг (крок D2), перед генерацією демо |
| Демо-меню до оплати                        | Так, але частково відкрите — див. умови в кінці розділу 2                  |

## 1. Модель даних

```ts
// src/lib/onboarding/types.ts

export type StepType = "question" | "info" | "loader";
export type QuestionType = "single" | "multi" | "number";
export type StepGroup = "goal" | "nutrition" | "body" | "finish";

export interface Option {
  value: string;
  label: string;
  description?: string; // пояснення під варіантом (патерн /diet_type)
  isNone?: boolean; // «нічого з переліченого» — знімає інші вибори
}

/** Усі предикати в масиві поєднуються через AND. */
export interface Predicate {
  field: string; // ключ у відповідях
  op: "in" | "notIn";
  values: string[];
}

export interface Step {
  key: string; // стабільний id: маршрут + аналітика + сховище
  type: StepType;
  group: StepGroup;
  title: string;

  /** Пояснення «навіщо питаємо». За замовчуванням видно лише новачкам. */
  hint?: string;
  hintAlways?: boolean; // показувати незалежно від nutritionKnowledge

  // --- question ---
  questionType?: QuestionType;
  field?: string; // куди пишемо у OnboardingData
  options?: Option[];
  min?: number; // для number
  max?: number;
  unit?: string; // 'см' | 'кг' | 'років'
  consent?: { text: string; href: string }; // точкова згода на екрані питання

  // --- info / loader ---
  body?: string; // основний текст
  bodyShort?: string; // варіант для «просунутих»
  variants?: Record<string, { title?: string; body?: string }>; // текст під відповідь
  variantOn?: string; // поле, від якого залежить variants

  condition?: Predicate[]; // крок показується, якщо всі предикати істинні
  analyticsEvent?: string; // за замовчуванням `onboarding_${key}`
}
```

Рішення по умовах: одного плоского масиву `AND` достатньо для всього нашого флоу.
Групи `and/or`, як у BetterMe, не вводимо, доки не з'явиться реальний кейс.

### Демо-меню до оплати — умови реалізації

Ідея сильна, але має чотири вимоги, без яких її не можна запускати:

1. **Email — до генерації, не після.** Інакше ми платимо OpenAI за кожного
   випадкового відвідувача і бота, не отримуючи навіть ліда. Тому D2 (email)
   стоїть перед D3 (лоадер).
2. **Показуємо частково.** Сніданок — повністю, з рецептом. Обід і вечеря —
   назва, фото, КБЖУ, час готування; рецепт під замком. Інакше «приклад»
   покриває потребу і знімає причину платити.
3. **Rate limit + фолбек.** Ліміт по IP через існуючий
   [checkRateLimit](../src/lib/rateLimit.ts). Якщо генерація впала або
   вийшла за таймаут — показуємо заздалегідь заготовлене меню під найближчий
   типовий профіль, а не помилку. Помилка в цій точці воронки коштує дорожче,
   ніж неідеальна персоналізація.
4. **Новий ендпоінт.** `/api/menu/generate` не підходить: він вимагає активної
   підписки і профілю в БД ([route.ts:33-53](../src/app/api/menu/generate/route.ts#L33-L53)).
   Потрібен `/api/menu/preview` — без авторизації, приймає відповіді квізу,
   рахує `goalCalories` через `calcCalories`, генерує один день, нічого не пише
   в `weekly_menus`.

Перед запуском — прогнати ~50 генерацій на типових профілях і переглянути
найгірші результати. Одна дивна страва на екрані-вітрині зашкодить сильніше,
ніж відсутність демо.

## 3. Механіка `nutritionKnowledge`

Керує **обсягом тексту**, а не кількістю екранів — інакше поплив би лічильник кроків
і зникли б елементи довіри.

| Рівень         | `hint` під питаннями | Текст інфо-екранів  |
| -------------- | -------------------- | ------------------- |
| `beginner`     | всі                  | `body` (повний)     |
| `intermediate` | тільки `hintAlways`  | `body`              |
| `advanced`     | тільки `hintAlways`  | `bodyShort ?? body` |

Кроки A1–A4 йдуть до вибору рівня — там завжди повний варіант.

## 4. Архітектура

```
src/lib/onboarding/
  types.ts      Step, Option, Predicate
  steps.ts      STEPS: Step[] — увесь флоу
  engine.ts     visibleSteps(answers) · nextStep · prevStep · progress · verbosity

src/app/onboarding/[step]/page.tsx     один динамічний маршрут
src/app/onboarding/page.tsx            redirect → перший видимий крок

src/components/onboarding/
  StepRenderer.tsx      диспетчер за step.type
  QuestionSingle.tsx  QuestionMulti.tsx  QuestionNumber.tsx
  InfoScreen.tsx  LoaderScreen.tsx
  QuizLayout.tsx        крем-фон, «ПИТАННЯ N З M», «Назад», CTA
```

**Маршрутизація.** `/onboarding/[step]`, де `step` — це `Step.key`. Дає робочу
кнопку «назад» у браузері, шеровані URL і аналітику по кроках без окремого коду.
Невідомий або ще недоступний ключ → редірект на перший незаповнений крок.

**Прогрес.** `visibleSteps(answers)` рахує видимі кроки з урахуванням `condition`;
лічильник — по питаннях, не по всіх екранах (інфо-екрани не нумеруються).

**Сховище.** Без змін: `localStorage.onboardingData` через існуючі
[onboardingHelpers.ts](../src/utils/onboardingHelpers.ts). `/payment/plan` і
`/api/subscription/init` продовжують працювати як є.

## 7. Поза цією задачею

Кроки, позначені **П**, збираються, але поки не впливають на меню:
структура прийомів їжі захардкоджена в `buildSystemPrompt`
([generateMenuWithAI.ts:92-99](../src/lib/menu/generateMenuWithAI.ts#L92-L99)),
часу подачі в схемі меню немає.

Наступні окремі задачі:

1. Час і кількість прийомів їжі → промпт і схема меню.
2. Звички і тяга (`eatingHabits`, `cravings`) → підказки генератору та пуші-нагадування.
3. `foodTracking`, `confidence` → сценарії мотиваційних сповіщень.
4. `targetWeight` → графік прогресу і прогноз дати досягнення цілі.
5. `/api/menu/preview` + фолбек-меню — окрема задача, від якої залежать кроки D3–D4.
   Квіз можна запускати раніше за неї: до її готовності D3 показує лоадер
   з фіксованою тривалістю, D4 пропускається.

## 8. Додаток · Контекст сесії, на якій це узгоджено

Дата: 7 серпня 2026. Нижче те, що не увійшло в основні розділи, але пояснює,
чому спек саме такий — щоб не переобговорювати вже закриті питання.

### Як отримано референс BetterMe

Флоу не клікався вручну — структура витягнута з їхнього публічного API конструктора:

```
GET https://api.web-constructor.betterme.world/flows/quiz-flow/1453
```

544 КБ JSON: 68 кроків для жінок, 70 для чоловіків, з текстами, варіантами
відповідей, умовами розгалуження і токенами теми. `flow=1453` — це A/B-варіант
партнерської воронки; ID флоу видно в query-параметрі сторінки квізу, а сам
ендпоінт — у їхньому JS-бандлі (`webConstructorApiURL}/flows/quiz-flow/${e}`).
Якщо знадобиться перезняти або порівняти з іншим варіантом — цього достатньо.

Бренд-бук читався через експорт Google Slides у PDF (`/export/pdf`) — там живий
текст. PDF, збережений з браузера, не парситься: у ньому шрифти переведені в криві.

### Відхилені варіанти

| Варіант                                                            | Чому відхилено                                                                                                                                                     |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Для «просунутих» пропускати інфо-екрани                            | Поплив би лічильник «ПИТАННЯ N З M», і зникли б елементи довіри — а вони потрібні всім. Замість цього варіюємо довжину тексту                                       |
| Питати алергії / нелюбимі / улюблені продукти тегами в квізі       | Вільне введення = клавіатура на мобільному в середині воронки, найвищий ризик відвалу. У BetterMe до email немає жодного текстового поля. Перенесено в профіль      |
| Окремі питання «тип харчування» + «виключення»                     | Зайвий крок. Один мультивибір із варіантом «Їм усе» покриває обидва                                                                                                |
| Групи умов `and`/`or`, як у BetterMe                               | Надлишково — у нашому флоу єдина умова це `target_weight` під три цілі. Плоский масив `AND` достатній                                                               |
| Один екран зі стейтом замість маршруту `/onboarding/[step]`        | Втрачаємо кнопку «назад» у браузері, шеровані URL і поекранну аналітику                                                                                            |
| Повністю відкрите демо-меню перед оплатою                          | «Приклад» покриває потребу і знімає причину платити. Тому часткове розкриття: сніданок з рецептом, обід і вечеря — назва, КБЖУ, час, рецепт під замком              |
| Генерація демо до збору email                                      | Платимо OpenAI за кожного випадкового відвідувача і бота, не отримуючи ліда. Тому email на D2, перед лоадером                                                       |
| Вигаданий експерт на картці B13                                    | Елемент довіри, побудований на вигадці, працює проти довіри. Дочекались реальних даних                                                                             |

### Що це чіпає поза онбордингом

- **`/payment/plan`.** Три таблиці лейблів ([plan/page.tsx:22-44](../src/app/payment/plan/page.tsx#L22-L44))
  видаляються — підписи їдуть з `STEPS`. Блок `additionalGoal` теж. Поле email
  і чекбокс згоди на обробку даних переїжджають в онбординг; сторінка вже вміє
  підхоплювати збережений email, тож ламатись не має чому.
- **`/api/onboarding`** — заглушка, яка нічого не робить. Крок-лоадер може
  звертатись до неї, як зараз, або до `/api/menu/preview`, коли той з'явиться.
- **`OnboardingData` і `UserProfile`.** `dietaryPreferences` уперше заповнюється
  з онбордингу, а не порожнім масивом у [profile/route.ts:34-37](../src/app/api/profile/route.ts#L34-L37).
  Решту трьох масивів (`allergies`, `dislikedFoods`, `favoriteFoods`) там
  залишаємо порожніми свідомо — вони вносяться в профілі після оплати.
